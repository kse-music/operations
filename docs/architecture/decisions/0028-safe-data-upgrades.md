# ADR 0028：版本化数据升级与升级前一致备份

日期：2026-11-09。状态：已接受并实施。部分替代 [ADR 0017](0017-current-data-contract.md) 中拒绝已知旧数据库/配置的策略；插件执行协议、身份目录和凭据安全边界继续有效。

## 背景与选项

用户安装新版需要保留现有主机、偏好和秘密引用。仅接受当前 schema 或只给新库执行建表，会使覆盖安装后的旧数据无法启动；持续放宽 DTO 默认值又会掩盖损坏和未知格式。仓库历史提供 schema 1–9、应用配置 v1 和旧模型格式的明确依据。

可继续要求人工修复、引入独立迁移框架，或在现有 rusqlite 上维护连续 SQL 与配置转换。选择后者，复用 SQLite 事务和 Backup API，不引入另一种运行时/ORM，不恢复退役产品能力。

## 选择

新库与已知旧库走连续迁移链，数据库结构、应用配置和版本在一次事务提交。`BEGIN IMMEDIATE` 覆盖检查、备份和升级；备份通过独立只读源连接保留 WAL 中已提交页面，完整性/外键检查和落盘成功后才写原库。schema 10 起保留名称与换行规范化 SHA256 历史，已应用 SQL 不修改。

配置独立版本化，转换只在存储边界发生，当前 IPC/DTO 严格校验。旧版可缺省字段补默认，已有值不替换；退役内容保留在完整备份或旧行。模型按首次使用独立升级，故障不阻断主机启动。未知版本、损坏和可能丢失数据的自定义结构明确拒绝，不猜测、不清库。

## 后果与限制

升级需要额外备份磁盘空间和启动时间，失败重试可能留下多个备份；不自动清理或恢复覆盖，用户决定恢复时必须考虑升级后新增数据。表重建暂关迁移连接的外键执行，但提交前强制检查，普通连接始终开启。备份和原数据同等保护，不包含系统凭据正文，迁移不读取/复制秘密或授予插件权限。

历史支持以明确 SQL/配置契约及测试为界，不承诺任意外部改库、未知未来版本、旧身份目录或旧插件协议。实现和扩展规则见[数据升级契约](../DATA_MIGRATIONS.md)，实际验证、失败与平台限制见[数据升级验证](../../validation/foundation/VALIDATION_DATA_UPGRADES.md)。
