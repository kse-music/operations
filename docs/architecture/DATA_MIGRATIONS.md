# 数据库与配置升级契约

## 当前版本和支持范围

| 数据                              | 当前版本 | 自动升级来源                           | 边界                                                   |
| --------------------------------- | -------- | -------------------------------------- | ------------------------------------------------------ |
| SQLite `user_version`             | 11       | 有历史 SQL 定义的 1–10；空库 0 初始化  | 无版本非空库、未来版本及不安全的自定义重建结构拒绝     |
| `application_settings.app_config` | 2        | 1，包括当时可缺省的新增偏好            | 当前格式仍严格校验，损坏/未知字段不猜测或重置          |
| `application_settings.ai_models`  | 2        | 注册表 1；尚无注册表时的旧 `ai_config` | 首次模型操作时独立升级，失败保留原数据，不阻断主机启动 |

窗口尺寸、本地模型授权、主机 SSH 选项、插件设置等当前未改变格式，原值保留。目录定位文件继续使用现有版本/状态机。插件 SDK/UI 和权限属于执行安全契约，不在本机制中转换或继承；旧身份目录及系统凭据服务也不自动搬迁。

当前 schema 包含 `plugin_mcp_servers`、`plugin_agent_tasks` 和 `plugin_agent_audit` 表；它们不作为当前助手的运行期数据源，也不表示提供 MCP 或持久任务恢复。迁移脚本及校验和属于现行升级链，必须保持不变。schema 11 在历史和配置校验通过后直接打开。

## 数据库迁移

实现为 `crates/storage/src/migrations.rs` 及 `crates/storage/migrations/`，使用现有 rusqlite（开启 backup 功能）和已使用的 SHA256 算法。新增结构变化追加连续 SQL 和注册项，提高 `DATABASE_VERSION`；不得修改已应用步骤。校验和统一 CRLF/LF，避免跨平台构建因换行差异拒绝历史。迁移历史从 schema 10 起必须完整，已记录的更早步骤同样校验。

1. 检查路径，开启 SQLite 连接并取得 `BEGIN IMMEDIATE`，序列化并发启动及外部写入。
2. 检查版本、历史和应用配置；当前数据直接使用。无版本非空库、未来版本和未知配置拒绝，保持原内容。
3. 升级前验证完整性和外键；涉及旧表重建时检查已知列和附属索引/触发器，避免丢掉用户附加字段或业务对象。
4. 通过另一个只读连接运行 SQLite Backup API，保存已提交页面与 WAL 内容。副本先写入独立 `.partial`，通过完整性/外键及源版本核验，关闭 SQLite、同步文件，发布完整 `.sqlite3` 后才允许修改原库。
5. 顺序执行结构步骤，在同一事务写入迁移历史、升级后的应用配置和 `user_version`，完整性及外键检查通过后提交。重建期间仅迁移连接暂关外键执行，提交前强制验证；普通业务连接保持外键开启。

新库走同一 SQL 链并初始化当前配置，无旧数据需要备份。版本 5 的退役任务数据若已存在则原样保留，不在新库创建退役功能；旧附加表、tags、秘密 GC、指纹、主机和凭据引用均不因升级清理。`crates/storage/tests/fixtures/schema-9.sql` 是受支持版本的独立升级回归夹具。

## 配置迁移

应用配置 v1 → v2 只补充旧契约允许缺省的 `interfaceFontSize`、`transferConcurrency`、终端/产品偏好及组内缺省字段。字号 `extraSmall` 转为 `small`；退役 `tasks` 快捷键退出当前运行配置，原内容保存在完整升级备份。已有值（包括布尔 false、用户快捷键、超时和凭据引用）优先保留，不覆盖显式 null、非法值或未知字段。转换后执行当前 AppConfig 校验，保存时沿用原更新时间；v2 缺少必填字段视为损坏，不通过迁移额外补默认，现有可选字段规则保持。配置和数据库版本独立，可在结构已经最新时单独升级配置。

模型注册表 v1 → v2 在模型读写事务中完成，补旧契约缺省的上下文窗口，退役旧价格字段；模型 ID/名称/修订/秘密引用不变。无注册表的旧单模型转换为“默认模型”，保留旧设置行。原始价格等退役内容仍在备份中。已存在注册表优先，不能从旧行复活已删除模型；未知版本或损坏只返回模型功能错误。模型故障不进入 Database::open 的启动依赖。

JSON 迁移拒绝重复字段和未知字段；IPC 不放宽旧格式校验。未来偏好/模型字段变化应增加自己的新版本和明确转换，不靠常驻 serde 默认值掩盖未迁移数据。秘密材料始终留在系统凭据库，迁移不读取、复制或重新授权密码、私钥和 Key。

历史默认值固定在 `migrations/app_config_v1_defaults.json`，旧模型上下文缺省固定为当时的 131072；不引用未来可能变化的新用户 Default。每一步只写固定目标版本，新增版本需追加后继转换，不通过修改当前版本常量让旧数据跳过中间步骤。

## 失败、备份与恢复

备份位于数据库旁 `migration-backups/<数据库名>.before-schema-<原版本>-<随机ID>.sqlite3`。使用新建文件和私有目录权限，拒绝链接/Windows 重解析点。备份失败不执行升级；未发布的 `.partial` 不是可用恢复副本。每次成功升级或模型首次转换留一份备份，幂等重开不新增；失败重试可能保留多份证据，不自动删除或覆盖。

SQL/校验/配置失败会退出事务，旧结构、版本和配置保持；事务提交的 I/O 故障也会报告未完成，保留数据及已有备份以便核查，不伪装成功。`DATA_MIGRATION_FAILED` 暴露安全阶段，技术原因链保留在 Rust，日志不记录配置正文或秘密。

本机制只向前升级。旧程序读取新数据库会拒绝未来版本；恢复备份或降级必须正常退出程序、核对备份和升级后新增数据，再由用户另行明确授权，不能在启动失败时自动覆盖原库。备份包含主机元数据和秘密引用，应与应用数据同等保护；完整系统秘密不在 SQLite 备份中。

## 开发和验收

数据库结构变更同时更新 SQL、注册表、版本和升级夹具；配置变更提高独立版本并更新当前 IPC/前端类型。按 [AGENTS.md](../../AGENTS.md#10-数据库与配置升级) 执行支持版本、数据保留、并发/WAL、失败回滚/重试、历史校验、未来版本拒绝及业务启动回归。原生测试输出统一复用根 `target/`，复制 EXE 到 QA 后执行。安装器、真实平台和生产数据验收单独记录，不把夹具通过当成全平台承诺。

候选版本的原生和安装器升级验收见[发布检查表](../release/RELEASE_CHECKLIST.md)。
